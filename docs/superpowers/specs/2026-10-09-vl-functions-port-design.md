# Porting v1's VL functions into the vl-reports-mz queries

Date: 2026-10-09. Status: draft for review.

## Problem

"VL info" and "VL results" leave out six v1 columns, because v1 computes them with three SQL
functions we did not have. The Mozambique team sent the script on 2026-10-09:
`corlix/fixtures/Mozambique_views/openldr-functions-script.sql` (UTF-16).

| v1 column | View | v1 expression |
|---|---|---|
| `ReasonForTest` | viewVL_Info | `GetReasonForTest(ESCOL.LIMSRptResult)` |
| `HIVVL_ViralLoadResult` | viewVL_Result | `ViralLoadResultMerge(HIVVD.rpt, HIVVD.coded)` |
| `HIVVL_ViralLoadCAPCTM` | viewVL_Result | `ViralLoadResultMerge(HIVVR.rpt, HIVVR.coded)` |
| `HIVVL_Low_value` | viewVL_Result | `ViralLoadResultMerge(HIVVC.rpt, HIVVC.coded)` |
| `HIVVL_Viral` | viewVL_Result | `ViralLoadResultMerge(HIVVF.rpt, HIVVF.coded)` |
| `FinalViralLoadResult` | viewVL_Result | `ViralLoadFinalResult(merge(HIVVD), first non-blank of merge(HIVVR / HIVVC / HIVVF))` |

Today the queries return each observation's raw reported value and coded value instead
(`HIVVD_LIMSRptResult`, `HIVVD_LIMSCodedValue` and so on), and `ESCOL_LIMSRptResult` for the reason.
The script also defines `ViralLoadResultRange` and others; neither VL view calls them, so they are
out of scope.

## Constraint

A custom query is one read-only SELECT (`validateSelectSql` in CE). It cannot create SQL functions in
the warehouse. Every function becomes an inline SQL expression, generated by a helper in
`vl-queries.mjs` so the SQL stays readable and each rule is written once.

## The three functions

### GetReasonForTest

A fixed translation, as v1 has it:

| Input | Output |
|---|---|
| NULL | `Reason Not Specified` |
| `''` | `Reason Not Specified` |
| `Nao Prenchido` | `Not Specified` |
| `Suspect treatment failure` | `Suspected treatment failure` |
| `Repiticas apos AMA` | `Repeat after breastfeeding` |
| `Rotina` | `Routine` |
| anything else | the input unchanged |

As a `CASE` in the "VL info" SQL. This is Mozambique content in the pack, not CE vocabulary, so a
CASE in the pack's SQL is allowed (AGENTS.md section 8: system-specific queries ship as packs).

### ViralLoadResultMerge(reported, coded)

v1: if `reported` is NULL or `''`, return the description of `coded` from
`OpenLDRDict.dbo.LIMSCodedValues` (panels HIVVL and VIRAL), or `coded` itself when it has no
description. Otherwise return `reported`.

Two things the port must get right:

1. **The reported value without the coded fallback.** The queries' existing `rpt()` helper already
   falls back to `coded_value` when there is no text or numeric value. Passed to the merge, it would
   never be blank, and the merge would return the code where v1 returns its description. The merge
   takes `text_value`, else `numeric_comparator + numeric_value`, and only then looks up `coded_value`.
2. **The descriptions ship in the pack.** A code system and value set,
   `urn:openldr:mz:cs:vl-coded-results` / `urn:openldr:mz:vl-coded-results`, built from
   `OpenLDRDict_MZ.dbo.LIMSCodedValues` for panels HIVVL and VIRAL, the same way the POC and link
   site lists are built. The query joins the warehouse's `terminology_codes` on the value set URL and
   the code.

**Duplicate codes.** `LIMSCodedValues` has `LDL` four times ("Target not detected" ×3, "Nível de
detecção baixo" ×1), `NEG` four times ("Negative" ×3, "NOT DETECTED" ×1), `POS` and `INVAL` with two
descriptions each. v1's function reads them with no ordering, so SQL Server picks one. A code system
needs one display per code.

Provisional rule until the Mozambique team says which v1 shows (question 2 in `QUESTIONS-FOR-MZ.md`):
take the most frequent description per code, and on a tie the first in `(LIMSPanelCode,
Description)` order. That gives `LDL` "Target not detected", `NEG` "Negative", `POS` "POS",
`INVAL` "INVAL". The build writes the rule's choices into `build-summary.json` so they can be checked
against the sample data.

### ViralLoadFinalResult(result, capctm)

Inputs: `result` = merge(HIVVD); `capctm` = merge of the first of HIVVR, HIVVC, HIVVF whose reported
value is non-blank, else merge(HIVVR). Returns NULL when no branch sets it. v1's rules, in order:

1. `capctm` set and `result` NULL:
   - `capctm` is one of the error words → NULL
   - contains `<` or `>` → `capctm`
   - numeric → `capctm`
   - else → `INDETECTAVEL`
2. `capctm` NULL and `result` set:
   - `result` is an error word → NULL
   - contains `<` or `>` → `result`
   - else → `INDETECTAVEL`
3. otherwise (both set, or both NULL):
   - `result || capctm` is numeric → `capctm`
   - either is `Target not detected` or `NOT DETECTED` → `INDETECTAVEL`
   - the two are equal ignoring case → apply rule 2 to `result`
   - else → NULL

Error words: `POS`, `Positive`, `Invalid`, `INVAL`, `Valid`, `Indeterminado`, `NEGAT`, `Reactive`,
`Negative`. v1's comparison is SQL Server's default case-insensitive collation; the port compares
case-insensitively too.

**Two quirks reproduced on purpose:**

- Rule 3 with both NULL: `CONCAT(NULL, NULL)` is `''`, and `ISNUMERIC('')` is 0, so the result is NULL.
- Rule 3's numeric test runs on the two values joined together (`'20' || '1000'` is `'201000'`), as v1
  does. It reads like a bug, but the port matches v1, not intent.

**ISNUMERIC.** SQL Server's `ISNUMERIC` accepts more than a plain number: a leading `+` or `-`,
thousands commas, a decimal point, an exponent, currency signs, and surrounding spaces. `'1,000'`,
`'1e5'`, `'$5'` and `'.'` are all numeric to it. The port emulates this with a Postgres regular
expression covering sign, digits with commas, decimal point, exponent, the currency signs `$ £ € ¥`,
and surrounding whitespace. Known differences: SQL Server also accepts some odd forms (a lone `+`,
`$`, `.`, tabs), which the regex treats as non-numeric. None of these is a plausible viral load
result. Listed as a known limit.

**Formatting stays CE's.** Where `FinalViralLoadResult` returns a numeric input unchanged, it returns
CE's value: CE keeps the full numeric value (`61.736…` where v1 shows `62`), as the README already
says for the raw columns. Matching v1's rounding needs v1's rounding rule, which we do not have.

## Column layout

The six v1 columns return in v1's names and positions. The raw stand-in pairs
(`HIVVD_LIMSRptResult`, `HIVVD_LIMSCodedValue`, and so on, and `ESCOL_LIMSRptResult`) are removed,
since they existed only because the functions were missing. `HIVVL_VRLogValue` is unchanged.

## How it is tested

Packs have no automated test run in cdr-toolchain. A check script beside `build.mjs`,
`packs/vl-reports-mz/check-vl-functions.mjs`, runs the generated expressions against real Postgres
over a table of cases: every branch of the three functions, each error word, the quirks above, and
the ISNUMERIC forms (`'1,000'`, `'1e5'`, `'<20'`, `'> 10000000'`, `''`, NULL). It connects through
the CE warehouse's Postgres (the dev container) and exits non-zero on any mismatch. It is run by hand
before a pack release, like the build.

What it does not prove: that v1 and the port agree on real Mozambique results. That needs the sample
data (question 4). When it arrives: load it, run "VL results" and v1's `viewVL_Result` side by side,
and compare the six columns request by request.

## Delivery

- `vl-queries.mjs`: the expression helpers and the new columns.
- `build.mjs`: the coded-results code system and value set (two new steps, before the queries).
- `check-vl-functions.mjs`: the case table.
- `PACK.md`, `README.md`: the six columns move from "not provided" to provided; the duplicate-code
  rule and the known limits are stated.
- Pack version: next patch number (0.5.3 if 0.5.2 is published first).

## Out of scope

- `ViralLoadResultRange` and the other functions in the script.
- Rounding numeric results to match v1.
- Mapping FacilityType letters (waiting on Mozambique's `DisaGlobal`).
